# CAKING ブランチ統合方針

作成日: 2026-08-01

## 背景

別々のPCで `main` と `codex/phase0-to-phase7` の開発が並行して進み、互いの変更をマージしないまま、同じ機能領域が別々に実装された。

- `main`: `25614475ed365eec7b17ef0a56aba74cd49ee9f0`
  - 2026-07-25に追加された「Phase 1 実装 - ゲームループ強化」
  - 現在の画面設計、営業画面、ボトムナビ、注文・ミッション表示などのUIはこちらが優れている
- PR #2 / `codex/phase0-to-phase7`: `65f36ca52feccbac472ceafe197034af0b7adc58`
  - PR: https://github.com/anyhoe104-spec/caking-game/pull/2
  - ゲームロジックのモジュール化、自動テスト、画像素材、セーブ移行、装飾・スタッフ・Miruの実装はこちらが優れている
- 共通の分岐元: `7200ae0b86f9bb857e787b9693f4bcaf8e9ebe8b`

両ブランチは共通の分岐元からそれぞれ1コミット進んだ状態であり、PR #2 は現状 `mergeable: false` となっている。単純なマージや片方の破棄は行わず、意図的な統合が必要。

## 結論

**後発の `main` を画面・操作体験の基準とし、PR #2 の内部実装、テスト、画像素材を移植する。**

PR #2 をそのままマージして `main` のUIを上書きしない。また、PR #2 を内容未確認のまま閉じて破棄しない。

## 統合作業の推奨手順

### 1. 統合用ブランチを作る

最新の `main` から専用ブランチを作成する。

例:

```bash
git switch main
git pull --ff-only origin main
git switch -c integrate/phase0-to-phase7
```

既存のPRブランチ上で無理に競合解消を始めず、`main` のUIを確実に保持できる状態から作業する。

### 2. PR #2 から非競合ファイルを先に取り込む

優先的に取り込む対象:

- `src/game/` 以下のゲームロジックモジュール
- `test/game.test.js`
- `public/images/characters/`
- `public/images/backgrounds/`
- `public/images/recipes/`
- `public/images/ingredients/`
- `scripts/process_generated_assets.py`
- `docs/audio-sources.md`
- 必要なフェーズ記録
- `package.json` の `test` スクリプト

画像については、旧 `images/ingradients/` のスペルミスと配置を整理し、最終的に `public/images/ingredients/` を正とする。

### 3. `main` のUIからPR側モジュールを利用する

`main` の `src/App.jsx` と `src/App.css` を見た目の基準として維持しつつ、`App.jsx` 内に直接書かれたロジックを次のモジュールへ置き換える。

- `src/game/storage.js`: セーブ、V2→V3移行、不正値補正
- `src/game/business.js`: 営業開始、タイマー、日報、翌日への遷移
- `src/game/customers.js`: 顧客生成、注文照合、注文完了
- `src/game/missions.js`: ミッション生成、進捗、報酬の一度だけの付与
- `src/game/logic.js`: 成功判定、経験値、ポイント計算
- `src/game/shop.js`: 装飾購入・装備、スタッフ雇用・効果
- `src/game/engagement.js`: レシピ評価、Miruの状況別メッセージ
- `src/game/data.js`: 素材、レシピ、レベル上限などの共通データ

一度に `App.jsx` 全体を書き換えず、機能単位で置換して、その都度テスト・lint・buildを実行する。

### 4. 未完成画面を実装へ接続する

- 装飾タブ: PR側の購入・装備処理へ接続する
- スタッフタブ: PR側の雇用・スタッフ効果へ接続する
- Miru: 画像、状態別表情、状況別メッセージを現行UIへ追加する
- 顧客: 絵文字フォールバックを残しつつ、収録画像を優先表示する
- レシピ: 収録画像と評価表示を接続する

### 5. 仕様差を決める

以下は両実装で値や挙動が異なるため、無条件に片方を採用しない。

- 営業時間: `main` は180秒、PR #2は300秒
- ミッション: `main` は固定3種類、PR #2は5種類から日替わり生成
- レシピ評価: `main` は大成功で段階的に上昇、PR #2は結果に応じた最高評価を保持
- 顧客の名前、好み、制限時間
- 当日売上目標の計算式

現時点の推奨は、営業のテンポを優先して180秒を維持し、ミッション生成と報酬処理はPR #2の方式を採用すること。その他は実機プレイで判断する。

### 6. `main` 由来の既知問題を修正する

2026-08-01時点で、後発 `main` はbuildに成功するがlintが6件失敗する。

確認済みの問題:

- 未使用の `MAT_KIDS`
- render中の `ref.current` 参照
- 空のブロック
- effect内での同期的なstate更新
- 日報表示をeffect経由で更新する構造

初期stateは `useState(() => loadSave())` などの遅延初期化を使用し、派生状態は可能な限り別stateにせず、イベント処理または現在stateから導出する。

### 7. 検証する

最低限、次をすべて成功させる。

```bash
npm test
npm run lint
npm run build
git diff --check
```

手動確認項目:

- V2セーブから進行状況を失わずV3へ移行できる
- オープニングから通常プレイ、エンディングまで進行できる
- 営業開始、タイマー、注文完了、時間切れ、日報、翌日遷移が動作する
- ミッション報酬が重複付与されない
- 装飾とスタッフの購入効果が保存後も維持される
- GitHub Pagesの `/caking-game/` サブパスで画像が表示される
- PWAインストールとオフライン再表示が動作する
- モバイル幅とデスクトップ幅で主要操作が隠れない

## 完了条件

- `main` の現在のUIと操作導線が維持されている
- PR #2にある必要な画像と実装済み機能が失われていない
- `src/App.jsx` から主要なゲームロジックが `src/game/` へ分離されている
- テスト、lint、build、`git diff --check` がすべて成功する
- GitHub Pages上で画像、PWA、ゲーム進行を確認できる
- 統合用PRを作成し、旧PR #2には統合先PRへのリンクを残してから閉じる

## 注意事項

- PR #2を先に閉じたり、ブランチを削除したりしない。
- `main` とPR #2の `src/App.jsx` を自動マージだけで確定しない。
- 画像を重複配置せず、公開パスを `public/images/` に統一する。
- 音源は `docs/audio-sources.md` のライセンス確認が完了するまで本採用しない。
- 作業開始時にGitHub上の `main` とPR #2のSHAが本書記載値から変わっていないか確認する。変わっている場合は、追加コミットを先に再評価する。
