## 2. 最終的な製品像

港町マサリエで古い菓子店を育てる製造・経営シミュレーション。
注文と原価・品質・生産能力を考えて製造販売し、店・設備・職人・レシピを成長させる。
現実の製菓・経営知識を収集し、季節催事や他店との競争・協力を楽しむ。
「遊ぶ → 学ぶ → 店が育つ → 現実の経験が新しいゲームコンテンツになる」という循環を作る。
初回ストア公開は通過点とし、ランキング・協力・コラボの運用が成立するところまでを最終目標とする。

|---|---|---|---|
|F01|菓子店経営|仕入れ・製造・注文・販売・日報を接続。売上、原価、利益、廃棄を見える化|1営業を完了でき、計算と在庫増減が一致する|
|F02|店舗・設備・職人レベル|店舗は客数/陳列、設備は容量/工程、職人は品質/習熟へ役割分担|強化前後の費用・効果・解放条件が明確で、保存/移行で維持される|

|F05|素材・設備の強化|素材品質や調達先、道具の熟練・改良を経営判断に接続|上位素材一択にならず、費用と品質/需要の選択が成立する|

|F07|イベント・コラボ|季節催事→外部パティスリー/作り手とのコラボへ拡張|開始終了、参加条件、報酬、終了後の閲覧、素材掲載期限を管理できる|
|F08|課金の検討と実装|装飾買い切りを先行。職人ノート/レシピ解説/経営編などの追加パックも比較|価格・提供範囲が明確で、購入/復元/返金を検証。ランキングの公平性を維持する|
|F09|他プレイヤーとの協力|非同期の共同注文・共同納品から開始|再送で二重加算されず、貢献・達成・報酬をサーバーで確定できる|
|K01|LLM Wiki制作基盤|Obsidian→公開用抽出→LLM生成→レビュー→ゲーム用JSON|私的情報を含めず、出典・承認・版を追跡して再生成/差戻しできる|
|K02|知識コンテンツ|製菓Tips、豆知識、原価/経営、攻略、職人の考え方、経験談、クイズ、図鑑・アイテム説明、レシピ紹介、イベント文|各種を生成/検査/表示でき、未承認データは配信されない|
|K03|知識解放・収集|販売数、原価率、職人レベル等でノートを解放|条件達成で一度だけ解放。収集済みは後から読め、旧セーブでも移行できる|
|K04|継続的な知識更新|新Tips、季節知識、新レシピ、職人ノート、経営編、プロ向け知識集を更新単位にする|同じ公開手順で追加・訂正・取り下げできる|

ショートケーキ100個販売、原価率30%以下、Lv10到達は解放条件の例であり、バランス確定値ではない。
短文Tipsはローディング時のほか日報・職人ノートでも表示する。読むために人工的な待ち時間を作らない。
クイズは解説付きで、基礎の経営プレイを不必要に止めない。実レシピはLLM生成のまま公開せず製菓経験者が確認する。
「Tipsそのものを売る」方針ではなく、知識が育つ継続的な編集・解説の価値を検討する。基本Tipsは無料を維持する案。

## 5. 実装・データ・実行環境

### クライアント

既存React/Vite＋Capacitorを継続。ショップ/製造の描画方式は完成品質見本で決める。
ゲーム進行、演出、保存、オンライン接続、購入権利を別の責務に分ける。
初期版はオフラインで店を育てられる。既存セーブとレシピ別装飾を維持する移行を必須とする。
ローカルの既存累計売上を公式ランキングへそのまま送信・採用しない。

### 知識の制作環境

Obsidian原本は私的な知識基盤として保持。許可したノートだけを手動またはスクリプトで書き出す。
商取引・顧客情報などを公開用データから除いた後、LLMで短文・クイズ・説明等を生成する。
JSONの構造検査→内容レビュー→写真/レシピ確認→PR→版付き公開を基本にする。
LLM呼び出しは開発・更新時。ゲーム実行時にWikiやLLMへの常時接続は要求しない。
実行ツール候補は既存Node/Pythonスクリプト、利用可能なLLM、GitHubのレビュー/検証。モデルや有料契約は試作結果で決める。
最初は同梱JSON、運用が増えたら版付きコンテンツ配信へ拡張する。

公開コンテンツには `id / type / title / body / tags / unlockRule / contentVersion / reviewStatus` を持たせる。
出典・許諾・確認者・訂正履歴は制作台帳で管理し、公開JSONへ出す項目を明示的に選ぶ。
未公開のObsidian本文・秘匿設定・個人情報をpublic配下や公開Git履歴へ出力しない。
実写真・実レシピはゲーム用レシピIDと対応づけ、出来高・単位・材料・工程を別のデータとして保持する。

### オンライン基盤

ランキング・協力の段階で、認証、API、DB、素材配信、集計ジョブ、監視、管理操作を追加する。
プロバイダーは未決定。採用前に無料枠だけでなく月額上限、運用負担、データ復元、契約条件を比較する。
最初は非同期方式。リアルタイム接客対戦、自由チャット、プレイヤー間の自由取引は初期対象外。
公式競技はサーバーが発行する参加IDと条件で開始し、サーバー時刻・規則・資源残高で行動を検証する。
クライアントが申告した最終売上だけを信用せず、採点可能な注文/製造/納品をサーバーで記録する。
協力の納品は冪等キーとトランザクションで二重計上・二重報酬を防ぐ。
オフライン育成とオンライン競技を区別し、通信失敗時の再送・保留・期限切れを仕様化する。

主要データ: `player`, `shopProgress`, `equipment`, `materialGrade`, `recipeUnlock`, `knowledgeUnlock`,
`eventDefinition`, `eventEntry`, `verifiedAction`, `leaderboardSnapshot`, `cooperativeOrder`, `contribution`, `rewardClaim`, `purchaseEntitlement`。
公開プロフィールを最小限にし、アカウント削除・名前の不適切利用への対応・運営の訂正操作を用意する。
課金権利とゲームセーブを分離。同一ストアの復元とOS間の共有は別仕様として設計する。
